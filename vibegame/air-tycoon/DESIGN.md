# 航空大亨 AIR TYCOON　设计文档

> 设计真源：玩法 / 数值 / 素材 / 界面等实现细节。
> 项目定位与用法见 [`README.md`](README.md)。

## 玩法

一局 60 回合（每回合 = 1 个季度 = 60 秒）。核心是一个**城市经济等级成长飞轮**：

```
开辟航线 → 运送客货 → 城市开发度上升 → 经济等级提高 → 需求变大 → 收益更高 → 开辟更多航线
```

36 座真实城市（上海、北京、东京、伦敦、纽约……，6 地区 × 6 城）分布在全球，每座有独立的人口、富裕度、开发度。**只有通航的城市才会增长**，未通航的城市开发度会缓慢衰减——这是「交通促进地区发展」的机制化表达。

**航线数量与城市等级正相关**（2026-10-09 加）：每座城市能承接的航线有硬上限 `cap = 该城等级`，**基地城市额外 +homeRouteBonus（默认 2）**——Lv5→5 条、Lv4→4 条……Lv1→1 条。口径：**每航司各自计数**（玩家与每个竞对各算一份，不是全网共享的池子），且**只挡新开线、不追溯**（城市降级不会强拆已开通的航线）。于是「上限」本身也随飞轮成长——通航 → 开发度涨 → 升级 → 解锁更多航线，扩张因此有节奏、有取舍。「航线随便加」不再成立。

**基地建立成本与维护费**（2026-10-09 加）：建立分基地的费用按城市等级差异化（`AT.buildBaseCostOf`）——高等级枢纽城市地价更贵：Lv1→180 · Lv2→240 · Lv3→300 · Lv4→420 · Lv5→570 万（基准 `buildBaseCost` × `buildBaseCostByLevel` 倍率表）。基地不是一次性投资：每季还需付维护费 `baseMaintOf = Σ baseMaintPerQuarter × level`（默认 10 万/等级/季，主基地同样计），让「广设基地」有持续成本而非无脑铺。地图上**只有基地城市用实线环**，已通航但未建基地的城市用虚线环（仍以归属色着色，只是环型不同）——视觉上区分「这是我的基地」与「这里通航了但没建基地」。

**回合节奏**：每 60 秒走完一个季度，结算收入与各项成本，然后可能弹出一张事件卡（原油跳涨、廉价航空入场、飞行员工会罢工、超强台风……）。**任何阻塞型弹窗与面板在屏时，回合计时都冻结**：事件卡必须做出选择才能继续（`state.card` 冻结计时，读卡期间 `t` 完全不累加）；季度结算报表、终局面板与底部抽屉面板（航线/机队/新航线/对手）同样冻结计时，关掉即恢复——且恢复后是**完整的一整季**，不会「刚关掉就跳季」。（2026-10-09 修：此前季报表在屏时计时照走，玩家读完一屏，下一季已经自己跑掉了。）

**双瓶颈设计**（本作核心判断点）：每条航线扩张时都会先撞上两种约束之一——

| 瓶颈           | 症状           | 正确应对               |
| ------------ | ------------ | ------------------ |
| **需求瓶颈**（薄线） | 客座率上不去，航班卖不满 | 降频、换小机型、或干脆放弃      |
| **槽位瓶颈**（干线） | 时刻排不进去，加频被夹回 | 换大机型（槽位按航线给，与机型无关） |

时刻上限刻意做成**反直觉**的：枢纽越拥挤，你能拿到的每日班次越少；竞对占位还会进一步扣减。所以「上海—东京」这类黄金线的槽位很紧张，而冷门长程线反而宽松——但冷门线又常常需求撑不满。玩家每次扩张都要先判断「这条线卡在哪」。

**五个 AI 竞对会主动反击**（不是背景板）：

| 行为      | 机制                                      | 玩家感受到的压力        |
| ------- | --------------------------------------- | --------------- |
| 抢线占槽    | 竞对每回合可能开通新线，占掉该城市的时刻配额                  | 你想开的黄金线可能已经排不进去 |
| **价格战** | 竞对可对**某一条**线发起价格战，持续 3 个季度，期间该线票价 ×0.86 | 你那条最赚钱的线突然不赚钱了  |
| 规模扩张    | 竞对按自身节奏增开航线、扩大机队                        | 榜首会被逐步拉开        |

价格战**只打压具体某条线**、不波及全局，所以顺手的应对是「换战场」——把运力挪去竞对尚未染指的线，而不是在原线硬扛降价。

（**竞对就是你没选的那五家航司**：开局选定一家后，其余五家按各自基地成为 AI 竞对——一洲一家，格局天然分散。）

### 并购对手（用户 2026-10-08 拍板）

「净资产榜超越对手」之外，玩家还能**整体并购一家竞对**：吃下它的全部航线与机队，对手彻底退场。

- **资格（两条同时满足）**：① 你的净资产排名**高于**目标；② 现金 ≥ 报价。前者意味着你得**先赢过它**才吞得下它——并购是「领先的兑现」，不是「翻盘的捷径」，避免中后期现金充裕就无脑收购。
- **报价**：对手净资产（现金 + 机队重置价 ×0.85）× `acquirePremium`（默认 1.35）；对手现金告急（低于 `acquireCrisisCash`）时改按 `acquireCrisisMul`（默认 0.70）**折价**，给出「趁你病要你命」的战术窗口。下限 `acquireMinPrice` 防止负现金对手被白嫖。
- **后果**：机队与航线整体并入（航线按运力降序贪心派机，每条并入线尽量给满 1 架；飞机池用尽后的剩余航线会被跳过）、该对手发起的价格战一并结束、它从榜单移除。商飞机型随并购转移不受「仅国航可采购」限制——`exclusive` 约束的是**购机资格**，不是**持有资格**。

> 本条机制放宽了原设计原则「竞对不可消灭，只能超越」，现在是「**可超越，也可并购**」。逻辑唯一真源：`S.acquireInfo`（资格 + 报价）、`S.acquireRival`（执行）；UI 唯一入口是底部「对手」Tab（`renderRivals`）。

### 开局选航司（用户 2026-09-29 拍板）

进入游戏前先在六张航司卡里选一家。每家**各据一个大洲**，基地即该洲枢纽城市，因此「选哪家」同时决定了开局的地理位置与战略取向。每家带一个**纯被动特色技能**（无主动操作、无冷却），数据唯一真源是 `data.js` 的 `AT.AIRLINES`：

| 航司     | 大洲 / 基地   | 现实原型       | 特色技能                                   | 开局机型         |
| ------ | --------- | ---------- | -------------------------------------- | ------------ |
| 中国国际航空 | 东亚 · 北京   | 东亚载旗全服务航司  | **规模经济**：全机队持有成本 −20%                  | 商飞 ARJ21     |
| 新加坡航空  | 东南亚 · 新加坡 | 高端服务型枢纽航司  | **服务品牌**：起始声誉 65（默认 50），声誉对需求与票价的影响 ×2 | 空客 A321neo   |
| 英国航空   | 欧洲 · 伦敦   | 欧洲老牌跨洋枢纽航司 | **联盟网络**：所有航线时刻槽位 +15%                 | ATR 72-600   |
| 联合航空   | 北美 · 芝加哥  | 北美规模网络航司   | **雄厚资本**：起始资金 +50%，贷款额度 +50%           | 波音 737-800   |
| 阿联酋航空  | 中东 · 迪拜   | 中东超级中转航司   | **中转枢纽**：航线一端在基地地区、另一端在外部时，需求 +25%     | 波音 737 MAX 8 |
| 澳洲航空   | 大洋洲 · 悉尼  | 大洋洲区域霸主    | **区域深耕**：基地所在地区城市开发度增长 +40%            | 空客 A320neo   |

**命名决策**：早期版本约定「竞对用虚构名、不影射真实航司」（见 sim.js 的 `RIVAL_NAMES`），本次经用户明确拍板改为**使用真实航司名**——理由是这样玩家一眼能认出「这家像谁」，技能与其现实原型（规模、服务、联盟、资本、中转、区域）对得上。`RIVAL_NAMES` 仍保留，供**不传** **`airlineId`** 的旧调用路径使用。

> 兼容性：技能全部读 `state.trait`，且所有乘数在缺省时为 1（见 `AT.NEUTRAL_TRAIT`）。因此不传 `airlineId` 的旧调用（headless / balance / audit 等工具）行为与首版完全一致：基地 C01、资金 800 万、声誉 50、虚构竞对名。

**航司识别色（`AT.AIRLINES[].color`）的三个落点**：① 选航司卡片的预览；② 地图上的**航线弧线**（`ARC_TINT` +30% 白）与**客机**（`PLANE_TINT` +32% 白 / `PLANE_TINT_RIVAL` +42% 白）；③ 面板「竞争对手 / 全球排名」每行的**色点**（`S.ranking()` 的 `color` 字段，UI 只做 `background:<color>` 拼串）。三条链同源，玩家才能把「榜上这一行」和「地球上那条线」对上号。客机提亮量于 2026-10-09 从 0.55/0.72 降至 0.32/0.42 —— 原值把六家航司色都拉到接近白色，飞机分不出谁是谁；降后航司识别色（红/橙/绿/蓝/紫/玫红）饱和显现。

| 位置 | 取值 | 说明 |
| --- | --- | --- |
| 玩家行 | `state.airlineColor` | 所选航司的识别色；旧路径为 `null` → 回落暖金 `#F5C542` |
| 竞对行 | `r.color` | 该家航司的识别色；旧路径无此字段 → 回落灰蓝 `#8C93A8` |

> ⚠ **别把色点写死成常量**：本题曾是五家竞对共用一个灰蓝 `#8C93A8`，玩家在面板上分不出谁是谁——而这条链断了**不报错、不白屏**，属于「静默失效」那一类（同见下文「六个『静默失效』的坑」）。判据不是「色值字符串互不相同」，而是**感知色差**：`tests/headless.js` 的「榜单归属色层」用 CIEDE2000 断言六色两两 **≥ 15**（8px 色块并排的可分辨下限）。被测出的真实反例：暖金 `#F5C542` 与新加坡航空橙 `#EF9F27` 只差 **12.3**，故玩家侧也改成自己的航司色，全盘最小值升到 15.7（国航红 vs 澳航玫红）。朝白插值只降饱和、**色相漂移 0°**，所以面板点与地图弧线读作同一支色。

> 补一条反过来的教训（2026-10 夜面灯火）：**ΔE 够大也可能是假的可分辨**。夜面旧灯火 `#FFF2E0` 与「我的城市」标记的 Lab ΔE 有 45.4，看着远超 15 的下限，但这点差距**全靠明度撑着**（色相 34.8° vs 37.3°，几乎没参与）—— 明度一旦被灯火拉平就彻底读不出来，实测叠加后 ΔE 掉到 5.1 乃至 0.0。所以「分得开」要分两个维度分别量：**色相要拉开**，**明度差要能在最坏的叠加环境下存活**（见「昼夜与夜景」的可读性口径）。

## 结局与评价

第 60 季度结束时，按**排名 + 综合分**给出五档评价（唯一真源是 `S.verdict(state)`；分项由 `S.verdictDetail(state)` 给出，UI 终局面板直接展示）：

综合分 = `规模 × 0.40 + 效率 × 0.35 + 覆盖 × 0.25`

| 分项   | 口径                                                     |
| ---- | ------------------------------------------------------ |
| 规模   | `max(净资产 / winNetWorth, 机队 / winFleetSize)`，封顶 1（「够大」门槛） |
| 效率   | 最近 **4 季平均净利率**，线性映射 `[8%, 20%] → [0, 1]`               |
| 覆盖   | `globalization` 百分比（通航城市 60% + 覆盖地区 40%）                |

| 档位         | 门槛                          | 称号     |
| ---------- | --------------------------- | ------ |
| `giant`    | 排名 ≤ 3 **且** 综合分 ≥ 0.68      | 全球航空巨企 |
| `major`    | 排名 ≤ 3，但综合分未达标（`desc` 会点名最弱的那一维） | 区域级强者  |
| `survivor` | 净值 > 0                      | 稳健经营者  |
| `failing`  | 净值 ≤ 0                      | 艰难维持   |
| `bankrupt` | 资金链断裂                       | 破产退市   |

> ⚠ **胜负必须用** **`tier`** **判，不要用** **`win`**。早期 UI 写的是 `S.verdict(st).win === true` —— `verdict` 从不返回 `win` 字段，该表达式恒为 `false`，「胜利」分支实际永远走不到（靠另一个排名条件偶然兜住）。已统一为 `tier === 'giant'`。

> **2026-10-09 改多维（D2）**：旧的 `giant` 是「排名 ≤ 3 且（净值 ≥ 6 亿 **或** 机队 ≥ 40 架）」，而实测终局净资产中位数已到 **1,056 亿**（balance 40 局：中位 10,558,932 万元）、平均机队 **106 架** —— 两个门槛形同虚设，`giant` 实际退化为「排名前三」。于是「堆机堆线但单位效率差」与「精耕细作」拿同一个评价，玩家没有理由优化效率。现改为综合分制：**「大而低效」不再自动等于巨企**。40 局自动对局实测：巨企 ×36 / 稳健经营者 ×2 / 区域级强者 ×2（效率分 0.90~0.97，说明效率维是活的，而不是人人满分）。

**频次玩法**（真实性与游戏性的妥协）：一架飞机代表同类机型的全部航班。单条航线最高每日 20 班，一架机最多承担每日 6 班；提升频次直接抬高变动成本。所以「加频」不是无脑操作，而是在需求、槽位、成本之间找平衡。

## 晚期经济（2026-10-09 重定）

针对「后期无脑加开航线、玩法单一」的系统性改造，五条机制都只改**成本侧与评价侧**，不动需求模型与单位口径：

| 机制 | 做法 | 关键参数 |
| --- | --- | --- |
| A0 资本成本 | 飞机持有成本率 0.045 → **0.70**（与 `nonFuelCoef` 0.155 → **0.12** 成对重定） | `ownershipPerQuarter` / `nonFuelCoef` |
| A0b 闲置机计费 | 未投入航线的飞机同样付持有成本（旧版只对停场机收半价维护费） | `idleOwnershipMul` |
| A1 机队老化 | 维护费 ×`(1 + 0.02 × 该线平均机龄)`；配「整队换新」一键动作（`S.renewRouteFleet`） | `maintAgePerQuarter` |
| A2 规模不经济 | 管理费 `60 + 12 × N²`（原 `60 + 8N`）；同城自营航线越多、时刻槽位越紧 | `overheadPerPlane` / `slotCrowdPerRoute` |
| D2 多维终局 | 见上一节 | `verdict*` |

**实测对照（60 季托管，3 种子均值）**：终局净利率 **29.2% → 18.1%**；维护+持有占航线成本 **3.2% → 18.9%**；管理费占收入 **0.05% → 5.7%**（真实航司销售管理费用率 5~8%）；平均航线 **22 → 17 条**。开局「2 架起始机飞最佳短线」净利率 18.1%（原 20.1%），仍可盈利。

> ⚠ 一个必须知道的设计后果：**开户即空转的玩家会烧穿现金**（约 5~6 季）。这不是 bug，而是「闲置即亏损」的直接体现；测试里需要隔离财务因素的用例（如并购层）已改为**先注资再推进**。

> ⚠ 残留与未做：① 只调持有率**修不了「买机回本 0.5 季」**（回本期 = 机价 ÷ 单机季净利，只由机价决定），要修得整体重排机价与一串等比常量；② 机龄只对玩家生效（竞对机队是抽象计数、不带机龄），故 A1 是**玩家侧的管理技能**；③ 两个最弱的竞对（起始资金 1000 / 900 万）在新成本结构下会萎缩到 2~7 条线、现金转负（5 局 40 次实测均如此）—— 竞对模型缺信用线与航线选择优化，属「组 C 竞对原型」的待办。

> **`exclusive`** **购机资格**：商飞 ARJ21 / C919 标 `exclusive: 'al_ca'`——现实中商飞机型几乎只由中国航司运营，故**仅中国国际航空可新购**。只挡「新购」、不追溯：旧存档或并购所得的商飞机仍可照常运营与加派（判定唯一入口 `AT.canBuyPlane`，见 [data.js](src/data.js)）。

**机型等级门槛**（2026-10-09 加，**替换**旧的开发度软惩罚）：大型客机需**航线两端城市**达到指定等级才可执飞——tier3（宽体 A330/787）需 Lv3、tier4（777/747）需 Lv4、tier5（A380）需 Lv5；tier1（支线）/ tier2（窄体）不限。**硬禁**，在**开线 / 派机 / 换机型**三处统一校验（`openRoute` / `assignPlane` / `upgradeRouteType`），口径唯一真源 `AT.planeLevelMin`（门槛表 `CONFIG.planeGate.minLevelByTier`，见 [data.js](src/data.js)）。只挡**飞行**、不挡**购机**——可以先买一架，等城市养到 Lv5 再投入；**只挡新增、不追溯**，旧存档或并购所得的越级机型照常运营。这条规则与航线上限一起，让「后期无脑堆 A380」不再成立：能停 A380 的只有两端都养到 Lv5 的全球枢纽线。

**升级链是主要的增长出路**：槽位按航线分配、与机型无关，所以当一条线的槽位被填满后，换更大的机型才能继续增长（也受上述机型等级门槛约束——得先把两端城市养到相应等级）。面板里的「换机型」按钮就是这条路径。

**单线架数有硬上限**：一条航线最多容纳 `floor(min(每日 20 班, 该线槽位) ÷ 每架每日班次)` 架飞机——超出时 `assignPlane` 直接拒绝，面板上的「加 1 架」也会置灰并给出原因。上限之外的那架机「飞不满自己的班次」，所以加了也只是白付持有成本；缺运力请换更大机型或调低频次档位，而不是继续堆机。

## 音频

全部音效与 BGM 都由 WebAudio **现场合成**，包里没有任何 `.mp3` / `.wav`。

**为什么不放音频文件**：① 小工具红线禁止外部资源，音频文件得随包走；② 本作只需要十来个一秒以内的短音，采样文件换来的是几百 KB 包体和一次额外解码；③ 合成音能按参数变化（客座率越高越明亮、机队越大越厚），采样做不到。

**13 个音效**，按触发源分三档：

| 档位   | 音效                                                  | 触发时机                                            |
| ---- | --------------------------------------------------- | ----------------------------------------------- |
| 世界事件 | `quarter` `open` `upgrade` `rival` `event` `crisis` | 任何一方触发都会响（季度推进 / 开线 / 城市升级 / 竞对抢线 / 事件卡 / 资金告急） |
| 玩家指令 | `click` `confirm` `deny`                            | 只在自己操作时响，让「我做了这件事」有手感                           |
| 结算   | `profit` `loss` `milestone` `end`                   | 季报盈亏、里程碑、终局胜负                                   |

**BGM 三段落**按**公司规模**换段（不是按时间）：`startup`（< 8 条线，84 BPM）→ `expand`（8\~20 条，104 BPM）→ `global`（> 20 条或全球第一，120 BPM）。三段落是同一调性（D 大调）上的**逐层加法**而非换曲，听感上像「同一支曲子越走越开阔」——与「公司越来越大」同构。

**设计约束**：音效基频一律 ≥ 200 Hz。手机扬声器低截止在 500\~800 Hz，200 Hz 以下基本辐射不出来；defcon 为把 24\~196 Hz 的音救回来做了八度补偿层，本作直接从选音上避开——这是本作音频能比 defcon 短很多的原因。

**三条沿用自 defcon 的硬经验**：

1. **默认开启**。实测「默认静音 → 玩家全程无声打完一局，音效白做」。
2. **去抖要叠加升调而非丢弃**。密集触发时直接 `return false` 会得到「越热闹越安静」；本作最多叠 2 层、每层升约 3.5%。
3. **压缩器只给音效总线，BGM 单独走一条**。BGM 走压缩器会长期处在压缩态，把该突出的音效反压下去。

右上角 `♪` 是静音键。**刻意不做持久化**——每局重置为开启，是「宁可多响一次」的取舍（上次关掉可能只是当时不方便）。

## 昼夜与夜景

球面只有**一个太阳方向**（`render.js` 顶部 `SUN_DIR`，全仓唯一真源），主光位置、夜面压暗壳、夜面灯火壳三处都从它推出来。**开局时这个方向由玩家本机的真实时间算出**（`src/solar.js`：`Date()` → 日下点 → 经 `AT.geo.ll2v` 转成球面向量），所以「打开就像此刻的天色」——在武汉下午打开看到东亚夜面，在纽约上午打开看到北美被照亮。之后**整局不再移动**，这与玩法仍是自洽的：航司经营看的是网络与城市，昼夜循环不会带来任何决策，却会让「夜里灯火最密的东亚」时有时无。所以本作**做的是「按真实时间决定初始朝向」，不是「昼夜循环动画」**——这是刻意的取舍，不是没做完。

> ⚠ 由此带来一个必须处理的连带问题：**基地约有四成到一半概率落在夜面**。开局镜头对准的是基地，这时玩家第一眼看到的是一片夜面。刻意**不改太阳去迁就镜头**（那等于把「按真实时间」这个功能本身架空），改为开局 toast 一句「此刻你基地所在半球是夜晚，太阳在另一侧」（`render.openAtNight` 由基地法线与太阳方向点积判定）。

夜面由**两层同心球壳**叠出来（`buildNightLights()`）：`1.0008R` 的**压暗壳**（普通透明黑，`renderOrder −3`）按法线把夜面的线性亮度乘下去，`1.002R` 的**灯火壳**（加色混合，`renderOrder −2`）叠一层只有城市灯火的贴图，颜色由 `uTint` 给（**低彩度冷白 `#E6ECF6`**）。两层都不写深度、都排在航线与城市光点之下，半径也错开一档，让「先压暗、再点灯、航线浮在最上」的层次在绘制顺序与半径上同时成立。

**灯火为什么是冷白、为什么要压峰**：玩家实机反馈「夜面灯火和机场标记撞色，看不清」。拆开是两件事：① 旧灯火是暖金 `#FFF2E0`（色相 34.8°），而信息层几乎全是暖色（我的城市 37.3°、主场 38.3°、航线兜底 41.6°、客机兜底 45.4°、新加坡航空品牌 36.0°）—— 六个暖元素挤在 11° 内，旧灯火与「我的城市」的 Lab ΔE 有 45.4 却**全靠明度撑着**；② 更要命的是**截断**：bloom 链路的 `rtScene` 是线性 8-bit，线性值 > 1 一律变纯白，而标记恰好坐在灯火最亮的像素上 —— 模拟合成链，灯火核心处两色 ΔE 直接掉到 **0.0**。**所以只改颜色治不了**：换色后核仍会截断，色相信息照样被抹掉。

解法是「冷白 + 软膝压峰」两条一起上。软膝 `soft(x) = K + (x−K)/(1 + k·(x−K))`（`x > K` 段）的上界是 `K + 1/k = 0.4578 < 1`，所以截断**在数学上不可能**发生，与贴图峰有多高无关。**顺序不能反**：膝作用在 `lum × uGain` 之后，先给增益提核、再用膝按顶。

为什么不能改成「把 `gain` 调小」：贴图非黑像素 P99 = 0.945 而 P50 = 0.047（极暗底 + 极亮核），线性缩放两头绑死 —— 缩到核不截断，暗底先消失。`NIGHT_GAIN` 最终取 1.6，不是 1.9：扫描显示 1.6 → 1.9 核心只亮 20%（0.0246 → 0.0295），而灯火铺开的面积从 0.186 跳到 0.320（+72%）—— 过了拐点，加的增益全变成糊在标记上的雾。标定脚本 `tools/probe-night-gain.py`，完整扫描表在 README。

**夜面经纬网必须自己压暗。** 它是 `LineBasicMaterial` + `transparent: true`，**压暗壳压不到它**（理由见下文坑 ⑤）。现在在建几何时把晨昏线 `smoothstep(0.08, −0.26, dot(N, SUN_DIR))` 烘进顶点色，乘子由 1 平滑降到 `GRID_NIGHT = 0.28`；太阳方向整局不变（开局由真实时间定），所以烘焙只发生在建几何时与每次 `setSunDir()`，其余时刻零每帧开销。

夜面灯火贴图 `assets/earth-night.jpg` 用 `tools/make_night_texture.py` 从 NASA Black Marble 生成：按**暖度 R−B** 挑出灯光（原图灯光只占 0.31% 像素，海洋与陆地本身带冷蓝底噪，直接加色叠上去会把夜面糊成一片蓝雾），多半径高斯晕开（2026-10-09 半径由 260px 收到 80px，见 README「为什么『大海也是亮的』」），再过一道**陆地门**（与 `src/landmask.js` 同一份 1° 掩膜，含 1 格膨胀与海岸柔化 —— 原图海上的渔船编队才是「整片海都在发光」的主因），降采样到 2048×1024。外链 `.jpg` 在 `file://` 下会被 CORS 拒绝、当不了 WebGL 贴图，故由 `tools/gen-earth-night-tex.js` 内联成 `assets/earth-night-tex.js` 随包走（与 `earth-tex.js` 同一手法）。注意**贴图的暖色偏不会带到画面上**：着色器只读 `max(r,g,b)` 一路灰度包络，颜色 100% 由 `uTint` 决定 —— 所以改灯火颜色不要重做贴图，改贴图也改不了灯火颜色。

`NIGHT_GAIN`（1.6）、`NIGHT_SOFT_KNEE` / `NIGHT_SOFT_K`（0.18 / 3.6，上界 0.4578）、`NIGHT_DIM`（0.92）、`GRID_NIGHT`（0.28）都是实机标定值，取值理由写在 `render.js` 的常量注释里；对应的定量读数、取样口径与「灯火可读性」A/B 见 README 的「昼夜与夜景」一节。

**为什么夜面变暗不用调光，而用一层压暗壳**：这是本轮标定最重要的一个发现。把 `AmbientLight` 从 2.6 降到 0.25（−90%），夜面屏幕亮度只从 0.195 掉到 0.152 —— 因为夜面的**线性**亮度本就极低（≈0.03），而 sRGB 编码是 `pow(x, 1/2.2)`，把 0.03 抬到 0.20、把 0.006 也抬到 0.09。低值区在编码后被整体抬离黑色，「调灯」这条路对夜面几乎无效。必须在线性域显式乘系数，才能压到编码也抬不起来的量级。压暗只作用在夜面（乘 `night` 因子），**阳面逐像素不变**，不必为「夜更黑」牺牲玩家熟悉的白昼观感；三盏灯与 `exposure 1.15` 的原配方因此一个字没动。

## 架构约定（改动前必读）

**三层 UI 职责**：

| 层    | 内容                                                     | 是否阻塞计时                                                 |
| ---- | ------------------------------------------------------ | ------------------------------------------------------ |
| HUD  | 常驻读数（资金、净值、排名、航线数……），100ms 刷新，**只改** **`textContent`** | 否                                                      |
| 抽屉面板 | `routes` / `fleet` / `newroute` / `rivals` 四个面板，可开可关   | **暂停**（开面板置 `state.paused`，关面板恢复）                      |
| 模态层  | 事件卡 / 季报 / 终局                                          | **阻塞**（sim 的 `tick` 里有 `if (state.card) return state`） |

**UI 只调 sim 的导出接口，绝不自己重算利润/运力/槽位。** 一旦 UI 抄一份公式，迟早与 sim 漂移，玩家会看到两个不一样的数字。所有经营数值一律来自 `S.settleRoute` / `S.forecast` / `S.routeSlots` / `S.idlePlanes` 等。

**`state.card`** **就是事件对象本身**（`state.card = ev`），不是 `state.card.event`。

**`idealSeatsFor`** **返回「整条线需要的总座位量」**（内部假设 3 架填满槽位），不是单机座位数——容易误读，UI 文案需写「全线需约 N 座」。

**`openRoute`** **不自动购机**：要求先有闲置飞机。UI 的「开通」按钮做成了组合动作（没库存则先买再开），按钮文案会明确写出「购机 1 架并开通（XXXX万）」。

**球面往复运动的「方向」只能由周期相位推出，不能用弧上位置。** 位置在一个往返周期里被经过两次，`t<0.5` 与行进方向无关；采样的「前方一点」也不要夹取到 `[0,1]`（两端会退化成零向量）。统一走 `AT.geo.legAt(u)`，它有 headless 断言保护。详见「验证」一节的「飞机朝向」层。

**改任一数值前先看** **`src/data.js`** **的注释**。那里记录了需求模型的三次重大修正、槽位反直觉设计的理由、以及被废除参数（`marketShareK` 等）的失败复盘——避免重走弯路。

### 六个「静默失效」的坑（都实测踩过，改动时别改回去）

这类 bug 的共同点是：**不报错、不崩溃、断言也不红**，功能就这么静悄悄地不存在。

**① 事件选项的现金奖励只能结算一次。** `applyEffect` 的尾部统一处理 `e.extra.cash`；早先在 `demand_all` / `cost_all` 两个分支里也各加了一次，造成**双倍扣除**（「跟进降价」的 `extra.cash = -260` 实际扣了 520 万），而 `data.js` 的事件预览只算一次 → **UI 显示与真实结算不符**。新增 `extra.*` 效果时不要在各分支里重复处理。

**② 竞对的价格战必须真的进结算公式。** `state.priceWars` 曾经只被创建与递减、`settleRoute` 从不读取——竞对发起价格战对玩家**毫无影响**，日志里那行「价格战」纯属摆设。现在 `settleRoute` 会查 `routeAtWar(state, route.key)` 并乘 `CONFIG.rivalPriceWarMul`。改结算公式时注意别把这个引用丢掉（丢掉也不会报错）。

**③ 地区类事件修正按「航线两端所属地区」匹配。** `modMul(state, type, region, ca, cb)` 的后两个参数是航线两端城市；只有传了它们，`demand_region` 才可能命中。此前只按 `region` 精确匹配，而多数调用点根本不传 `region` → 地区性需求事件**永不生效**。

**④ 太阳方向只能有一处真源。** 主光位置、夜面压暗壳的 `uSun`、灯火壳的 `uSun` 必须都取自 `SUN_DIR`。一旦某处另写一份坐标，晨昏线就会错开：要么「白天那半边也亮着灯」，要么夜面亮起一盏与光照方向无关的灯 —— 两种都不报错，只是看着别扭。同理，灯火壳与压暗壳的晨昏线函数（`smoothstep(0.08, −0.26, dot(N, uSun))`）也必须一致，否则会露出一圈压暗没盖住的夜面。

**⑤ `renderOrder` 跨不过「不透明 / 透明」这条界。** three.js 先把**不透明**物体画完、再画**透明**物体，`renderOrder` 只在这个划分**之内**排序。所以给夜面压暗壳写 `renderOrder −3`，并不能让它先于任何 `transparent: true` 的东西绘制。经纬网（`LineBasicMaterial` + `transparent: true`）就是这么被漏掉的：注释里一直写着「经纬网属于不透明层、已先画完，所以会被压暗」，**实际上它一直在压暗壳之后绘制，夜面那半球的经纬网始终是全亮的**。这类错误的特点是：画面「看着不对」但没有任何一层会变红，除非有人真的去量化夜面某个元素的亮度。

> 排查手法：往场景里加任何「应该被压暗 / 应该被遮挡」的元素后，先问它在哪个批次（`transparent` / `depthWrite`），不要只看 `renderOrder`。要压暗夜面元素，走**顶点色烘焙**（经纬网现在就是这样：太阳整局不动，所以烘完就零每帧开销；关键是改太阳方向时必须重烘）或在自己着色器里乘 `night` 因子。

**⑥ 发光元素的颜色不能靠贴图，要看着色器读了什么通道。** 夜面灯火贴图明显偏暖（按 `R−B` 挑出来的），但画面上灯火是冷白 —— 因为着色器只读 `max(r,g,b)` 一路灰度包络，颜色**全部**由 `uTint` 决定。于是「改贴图来调灯火颜色」是白费力气，而「改 `uTint` 却担心要重做贴图」是多余的顾虑。判断方法：进着色器源码看它到底用了贴图的哪个通道，不要从贴图外观反推画面颜色。
