# 航空大亨 AIR TYCOON（air-tycoon）

> **分类**：`#vibegame` 互动游戏　·　分类索引见根目录 [`TRACKS.md`](../../TRACKS.md)
> 小红书 VibeCoding 大赛参赛作品 · 框架复用自 [`../defcon`](../defcon)

一款 **3D 球面地图上的航空经营模拟游戏**，竖屏移动端单手游玩。**开局先在六家航空公司里选一家**（各据一个大洲、基地与特色技能各异），再开辟航线、购置机队、扩张网络，让交通带动城市经济成长；目标是在 60 个季度（15 年）内成长为**全球航空巨企**。

## 项目信息

- 中文名：航空大亨
- 仓库名：`air-tycoon`
- 主赛道：`#vibegame`（互动游戏）
- 复用来源：`vibegame/defcon`（球面 3D 引擎、竖屏单手 UI、无构建工程约定、测试三件套方法）

- 音频：WebAudio 程序化合成，**零音频文件**（见「音频」一节）


## 技术路线

- `index.html` + `src/` 下 10 个外置经典脚本，**无构建步骤**，作为小红书「小工具」上传挂载
- 竖屏移动端布局（390×844 基准）
- 3D 引擎：**three.js r149**（随包内联，608 KB）；渲染层 `src/render.js` 自写（球体、城市光点、航线弧、HUD 投射），含自动降级
- 音频：WebAudio 程序化合成（13 音效 + 三段落 BGM），**零音频文件**，见下节
- 逻辑 10 Hz 固定步长 + 渲染 60 fps 插值，确定性便于无头测试
- 红线：离线运行不联网、无 `fetch` / `Worker` / `eval`、脚本全外置、无外部资源
- 兼容基线：Chrome 61（无 CSS `inset` 简写、无 flex `gap`、`var()` 需兜底）


## 自动存档

每 5 秒写一次档（真实时间，见 `game.js` 的 `AUTOSAVE_SEC`），另在切后台 / 页面卸载（`visibilitychange` + `pagehide`）时立即补写一次；`phase === 'over'`（终局）时清档。启动时若读到**可读存档**，先弹「继续经营 / 开启新的一局」覆盖层（`ui.showResume`），点选后才建局（`boot` 必须在点击手势里执行以解锁 AudioContext）；没有可读存档则直接进选航司。

存储按小红书小工具规范 **§2.4 数据存储 / §3.6 版本判断 / §3.7 Storage JS API** 分两级，全部实现在 `src/save.js`：

- 客户端 ≥ 9.46（`buildVersion` 忽略末 3 位编译序号后 ≥ 9460）→ `window.xhs.miniTool.setStorage / getStorage / removeStorage`（规范推荐方案）；
- 客户端 < 9.46，或未注入端能力（普通浏览器预览）→ 降级 `localStorage`。

读写一律包在 `try/catch` 内，失败只返回 `false` / `null`、**绝不抛出**（规范明确浏览器自带存储不保证可用/持久），调用方必须容忍「读不到、写不成」。**全仓仅 `src/save.js` 允许触碰 `localStorage`**，`tests/check-chrome61.py` 有对应扫描项（⑤b）钉住这条边界。

存档是整局 `state` 的 JSON 快照，有两处不能直接 JSON 化：`rng` 是闭包函数，故另存 `rngState`（`sim.makeRng` 暴露了 `getState/setState`），复原时把随机流**接着往下跑**而不是从种子重放 —— 否则读档后的世界线会与「一直玩下去」分叉，破坏「同种子同结果」的确定性契约；`fx` 是每帧消费的瞬时特效队列，不存。读档时 `paused` 一律复位为 `false`：存档可能写在面板打开的暂停态，原样恢复会让 `tick` 永远早退、游戏卡死。


## 昼夜与夜景

**太阳方向按玩家本机的真实时间计算**（`src/solar.js`）：开局取一次 `Date()`，算出此刻的**日下点**（太阳直射点），再经 `AT.geo.ll2v` 转成球面向量，作为 `SUN_DIR` 的初值。所以在武汉下午打开，看到的是东亚的夜面；在纽约上午打开，看到的是北美被照亮——**天色与玩家所在时区自洽**。整局里太阳不再移动（与「昼夜循环不带来任何决策」的既有设计一致，见 DESIGN）。

太阳方向的**唯一真源**是 `render.js` 的 `SUN_DIR`，阳面明暗与夜面晨昏线由同一份方向推导，所以两处的分界永远严丝合缝。夜面效果由**两层同心球壳**实现，都在 `render.js` 的 `buildNightLights()` 里：
| 层 | 半径 | 混合 | renderOrder | 作用 |
|---|---|---|---|---|
| 压暗壳 | 1.0008 R | 普通透明（黑） | −3 | 按法线把**夜面**的线性亮度乘下去 |
| 灯火壳 | 1.002 R | 加色 | −2 | 叠一层只有城市灯火的贴图；颜色由 `uTint` 定 = **低彩度冷白 `#E6ECF6`** |

两层都 `depthWrite: false`、都排在航线/城市光点之下（它们 renderOrder 为 0 / −1），半径也刻意错开一档，让「先压暗、再点灯、航线浮在最上」的层次在绘制顺序和半径上同时成立。

> ⚠ **`renderOrder` 跨不过「不透明 / 透明」这条界。** 经纬网是 `LineBasicMaterial` + `transparent: true`，不管 `renderOrder` 写多小，它一律在**透明批次**里绘制 —— 也就是**排在 `−3` 的压暗壳之后**，压暗壳根本压不到它。此前注释里「经纬网属于不透明层、已先画完所以会被压到」的说法是错的，实测夜面经纬网一直保持全亮。现在改为把晨昏线**烘进顶点色**（太阳整局不动，所以烘一次就够；但开局那次也是真烘，见 `setSunDir()`），零每帧开销，见下面「夜面经纬网」。

### 太阳位置按真实时间算（`src/solar.js`）

`Date()` → **日下点**（`lat = 赤纬`、`lon = 15×(12 − 本机小时)`）→ `AT.geo.ll2v` → 方向向量。

三条必须写清楚的口径：

- **用「本机时间当作太阳时基准」**，不是 UTC。于是「本机 12:00 时，日下点落在本机经度上」，玩家在中午打开看到的就是白天 —— 这比天文精确更符合直觉预期。
  - ⚠ 代价：本机时区与经度不匹配时会偏移（中国用东八区、经度跨 73°E~135°E，最多偏约 30°）。这是**有意为之的简化**：本作要的是「打开就像此刻的天色」，不是天文台级的日下点。要精确就改 `subsolarPoint` 一处，但注意那会让「北京的玩家中午看到夜面」，反而更怪。
- **赤纬用 Cooper 方程形式** `23.44·sin(2π(n − 81 + 时/24)/365.24)`，不是更简陋的 `sin(2π/365·(doy−81))` —— 后者把极值日钉在 3/22、9/22，而真实在 6/21、12/21，误差可达数度（球面上就是晨昏线错开几百公里）。实测本式极值日准确落在 6/21（+23.44°）与 12/21（−23.44°），春分残留 −0.6°。
- **任何异常都退回常量** `[4, 3, 5]`（= 历史上那个固定机位，直射点 25.1°N/128.7°E）。宁可晨昏线停在旧位置，也不要让球体整个变黑或全亮 —— 后者不会让任何一层测试变红。

方向被**五处**消费，全部必须同源（`setSunDir()` 是唯一写入口，一次改齐）：

| # | 消费点 | 漏更新会怎样 |
|---|---|---|
| ① | `keyLight.position` | 球体明暗分界与晨昏线错开 |
| ② | `rimLight.position` | 冷补光不再正对夜面（恒取太阳反方向） |
| ③ | `dimMat.uniforms.uSun` | 压暗壳的晨昏线错开 |
| ④ | `nightMat.uniforms.uSun` | 灯火亮起的界线错开 |
| ⑤ | 经纬网顶点色（**几何里的快照**） | 网格明暗界线错开 |

①②③④ 是写一次就跟着走的，**⑤ 必须显式重烘**（`rebakeGridNight()`，17 条线 × 97 顶点 = 1649 次点积，只在 `setSunDir` 时跑）。③④ 共享**同一个 `Vector3` 实例**，所以必须用 `copy()` 原地改 —— 若写成 `uniforms.uSun.value = vec` 只会换掉其中一个壳，另一个继续停在旧方向。

**开局基地在夜面时给一句提示。** 真实时间下基地约有**一半概率**落在背光面（`render.openAtNight`，由基地法线与太阳方向的点积判），此时开局镜头对准基地、玩家第一眼看到的就是一片夜面。刻意**不改太阳去迁就镜头**——那等于把「按真实时间」这个功能本身架空。改为开局 toast 一句「此刻你基地所在半球是夜晚，太阳在另一侧」。

### 夜面变暗靠「压暗壳」，不靠调灯

这是本轮标定最重要的一个发现，也是**只靠直觉会做错**的一处。

夜面不够黑时，第一反应是「把环境光调低」。实测无效：`AmbientLight` 从 2.6 一路降到 0.25（降 90%），夜面屏幕亮度只从 **0.195** 掉到 **0.152**。原因是渲染管线的 sRGB 编码 —— 夜面的**线性**亮度本就极低（≈0.03），而编码是 `pow(x, 1/2.2)`：0.03 被抬到 0.20，0.006 仍被抬到 0.09。低值区在编码后被整体抬离黑色，所以「调灯」对夜面几乎无效（顺带一提，这也解释了为什么 `rim` 补光虽然正对夜面、却始终没能把夜面点亮多少）。

正确做法是在**线性域显式乘一个系数**，把线性值压到连编码都抬不起来的量级。压暗壳只作用在夜面（乘 `night` 因子），**阳面逐像素不变** —— 不必为了「夜更黑」牺牲玩家已经熟悉的白昼观感。三盏灯与 `exposure 1.15` 是一组配方，本轮一个字没动。

### 夜面灯火贴图

`assets/earth-night.jpg`（2048×1024）由 `tools/make_night_texture.py` 生成：按**暖度 R−B** 把真正的灯光从蓝调地表里挑出来（原图灯光只占 0.31% 的像素，而海洋/陆地本身带冷蓝底噪 —— 直接叠上去会把整个夜面糊成一片蓝雾），再做一层多半径高斯晕开，最后降采样。两段链路都可复现：

```
assets/earth.jpg (md5 e15eb8d2…)
   ── python tools/make_night_texture.py ──▶ assets/earth-night.jpg     (md5 c20572bd…, 39 KB)
   ── node   tools/gen-earth-night-tex.js ─▶ assets/earth-night-tex.js  (md5 6f51a046…, 53 KB)
```

两个前置条件写在脚本头注释里，改动前务必读：

- **源图必须与 `vibeknow/nobel-atlas` 逐字节同源**（两边 `earth.jpg` 的 md5 都是 `e15eb8d2…`）。等距圆柱投影是按 UV 对齐的，源图一换，灯光就会落到错误的海岸线上 —— 不报错，只是城市灯火整片偏移。
- **外链 `.jpg` 在 `file://` 下不能当 WebGL 贴图**（CORS 拒绝），必须内联成 `earth-night-tex.js`，由 `index.html` 用 `<script src>` 装 —— 与 `earth-tex.js` 同一手法。

夜景贴图是包内**第二个**内联 data URI，它和音频脚本属于同一类风险：脚本漏挂或漏进包时不会报错、console 干净，只是夜面的灯火**静默消失**。所以 `tests/verify-dist.py` 在提交包里对它单独点名（`render.nightOk`）。

> ⚠ 贴图虽然偏暖，但**渲染出来的颜色与贴图的色相无关**：着色器只读 `max(r, g, b)` 一路灰度包络，颜色 100% 由 `uTint` 决定。所以把灯火从暖金改成冷白**不需要重新生成贴图**；反过来，想让灯火变暖也别去改贴图，改 `uTint`。

### 夜面灯火为什么改成冷白 —— 以及「软膝压峰」

起因是实机反馈：**夜面灯火和机场标记撞色，看不清**。拆开看是两件独立的事，只解决第一件没用。

**其一，色相挤在一起。** 旧灯火是暖金 `#FFF2E0`（HSL 色相 34.8°），而信息层几乎全是暖色：我的城市点 37.3°、主场 38.3°、航线兜底 41.6°、客机兜底 45.4°、新加坡航空品牌色 36.0° —— 六个暖元素全挤在 11° 以内（只有 `virginHex` 197° 和 `rivalHex` 261° 是安全的）。旧灯火与「我的城市点」的 Lab ΔE 虽有 45.4，但这点差距**全靠明度撑着，色相几乎没参与**，一旦明度被灯火拉平就彻底读不出来。

**其二（更要命），截断。** bloom 链路的 `rtScene` 是**线性 8-bit RGBA**，线性值 > 1 一律截成纯白 —— 而标记恰好就坐在灯火最亮的像素上。按合成链（相加 → 8-bit 截断 → `lin2srgb`）模拟：灯火中段 `pk=0.55` 时灯火与标记的 ΔE 掉到 **5.1**，灯火核心 `pk=0.88` 时 ΔE = **0.0**（两边都是 `(1,1,1)`）。冰蓝的 virgin 标记同样（9.4 / **0.0**）。**所以只改颜色治不了**，必须同时压住峰值。

截断的实测规模：逐个探 29 个机场的贴图，**22 个**的 5×5 最大通道峰 > 0.70、**16 个** > 0.86（中位 0.878、最高 1.000）。在旧 `gain 1.9` 下 0.88 → 1.67，是硬截断。实机截图同口径：球面亮度 > 0.90 的像素占比，开灯 **0.45%** vs 关灯 0.04%（11×）。

**为什么不能直接调小 `gain`。** 贴图非黑像素的分布是 P99 = 0.945 而 P50 = 0.047 —— 极暗的底 + 极亮的核。线性缩放是「两头绑死」的：缩到暗底不消失，核仍截断；缩到核不截断，暗底先没了。所以需要的是**软膝**而不是缩放。

```
soft(x) = x                                 , x ≤ K
soft(x) = K + (x − K) / (1 + k·(x − K))     , x > K
```

上界 `K + 1/k < 1`（本仓 `K=0.18`、`k=3.6` ⇒ **0.4578**），所以这个函数**在数学上不可能**截断成纯白，与贴图峰有多高无关。对应常量 `NIGHT_SOFT_KNEE` / `NIGHT_SOFT_K`。

> ⚠ **顺序不能反**：软膝作用在 `lum × uGain`（增益**之后**）的值上。先给足增益把城市核提起来，再用膝把峰值按住。如果写成「先压后增益」，上界立刻失效，纯白斑原样回来。

增益是这样标定的 —— `tools/probe-night-gain.py` 在同一机位（东亚灯火面）固定软膝、逐档扫 `setNightGain`，每档与「灯火全关」那张配对：

| gain | 灯火提亮 `dInner` | 对比度保留 | 彩度保留 | 灯火铺开面积 `litFrac` | 纯白斑占比 |
|---|---|---|---|---|---|
| 0.0（全关·基准） | 0.0000 | 1.000 | 1.000 | 0.0003 | 0.000% |
| 0.6 | 0.0141 | 0.869 | 0.824 | 0.1286 | 0.037% |
| 1.0 | 0.0190 | 0.815 | 0.770 | 0.1701 | 0.041% |
| 1.4 | 0.0229 | 0.774 | 0.733 | 0.1814 | 0.041% |
| **1.6（取）** | **0.0246** | **0.756** | **0.719** | **0.1858** | **0.041%** |
| 1.9（旧值） | 0.0295 | 0.731 | 0.700 | 0.3201 | 0.044% |
| 2.4 | 0.0330 | 0.695 | 0.676 | 0.3249 | 0.050% |
| 3.0 | 0.0393 | 0.660 | 0.656 | 0.3408 | 0.054% |

取 **1.6** 的判据是 `litFrac`（灯火铺开的面积，也就是糊在标记上的那层雾）：1.4 → 1.6 只从 0.181 涨到 0.186，而 **1.6 → 1.9 一下跳到 0.320**（+72%）—— 同一档增益换来的核心亮度只有 0.0246 → 0.0295（+20%）。也就是说 1.6 之后再加增益，买的几乎全是「雾」而不是「灯」。软膝的上界 0.4578 决定了核心不可能无限亮，增益只会把**中段**一起抬起来，所以过了拐点就是纯损失。

> 同档重跑会有 ±0.003 的抖动（SwiftShader 光栅化非确定性），拐点位置不受影响；对比度/彩度保留列在同一次扫描内是单调的，可以作为趋势读。

### 夜面经纬网按晨昏线压暗

经纬网共 17 条（5 纬 + 12 经），白天用 `#86BAD8`。既然压暗壳压不到它（见上面的 ⚠），就必须自己处理，否则夜面会浮着一层全亮的白网，比灯火更刺眼。

做法是把同一份晨昏线函数 **烘进顶点色**：每个顶点按 `night = smoothstep(0.08, −0.26, dot(N, SUN_DIR))` 求夜面因子，乘子从 1 平滑降到 `GRID_NIGHT = 0.28`。材质相应改成 `transparent: true` + `vertexColors: true` + `opacity: 0.2`（`opacity` 是全局透明度，夜面的额外压暗在顶点色里）。太阳方向整局不变（开局由真实时间定），所以烘焙发生在建几何时与每次 `setSunDir()`，其余时刻零每帧开销。

探针读回**实际顶点色**而不是重算一遍，`gridProbe = { lines: 17, dayMul: 1.0, nightMul: 0.28 }`；断言挂在这个 getter 上 —— 把烘焙删掉、或改回单一颜色，断言立刻红。

### 标定读数与口径

「昼夜效果够不够」不靠肉眼，靠定量口径。`tests/smoke-render.py` 的 `sphere_lum` 取球面本体 **0.55R 圆内**的平均亮度：球心恒在屏幕正中（相机 `lookAt(0,0,0)`），`R_px = 0.2828 × H`，只取 0.55R 是为了避开球体边缘那圈大气辉光（它在 0.95~1.05 R 一带最亮，会把「夜面有多黑」整个淹掉）。

| 观察点 | 改前 | 改后 |
|---|---|---|
| 阳面（太阳直射点 25.1°N / 51.3°W） | 0.402 | **0.403**（读数噪声内不变，阳面 `night` 因子为 0） |
| 夜面（反足点 25.1°S / 128.7°E） | 0.207 | **0.118** |
| 昼夜比 | 0.514 | **0.292** |
| 开局主场视角 | 0.224 | **0.170** |

「改前」不是一句不可复核的历史读数：探针在两个机位把两壳一起关掉（`setNightDim(0)` + `setNightGain(0)`）复现同一读数（夜面实测 0.207、开局视角 0.224），再还原、确认差 < 0.01。

### 灯火可读性口径（本轮新增）

「灯火会不会把标记吃掉」同样要有口径，否则只能靠「我觉得看得清」。做法是**同机位 A/B**：东亚灯火机位分别拍「开灯 / 关灯」两帧，**样本取自关灯帧**里「明显亮于局部背景」的像素（局部背景用 15px 盒式模糊估计，判据 `前景 − 局部背景 > 0.10`）—— 用关灯帧挑样本，两帧的样本集才完全一致，否则一开灯样本自己就变了。

实测样本 497 个（占球面 0.92%）。`contraOn/Off` 与 `chromaOn/Off` 就是同一批像素在开灯/关灯下的平均对比度与平均彩度 `|R−B|`：

| 指标 | 改前配方（暖金 + 无软膝） | 现在（冷白 + 软膝） |
|---|---|---|
| 信息层对比度（前景 − 局部背景） | 0.249 | **0.277** |
| └ 相对关灯帧的保留率 | 0.68 | **0.75** |
| 信息层彩度 `\|R−B\|` | 0.174 | **0.226** |
| └ 相对关灯帧的保留率 | 0.55 | **0.72** |
| 纯白斑占比（亮度 > 0.97） | 0.21% | **0.05%**（降 4.2×） |
| 灯火把夜面提亮 | +0.031 | +0.025 |
| 灯火像素的平均变暖量 Δ(R−B) | 0.060 | **0.050** |

关灯帧基线（两行共用）是对比度 0.368、彩度 0.316。纯白斑**基线并非 0**：标记自身核心叠在灯火上也会截断，所以断言一律用**差值**而不是绝对值（见下）。

### 为什么夜景也要单独一层断言

因为**「机制写了」和「机制生效」是两件事**，而这一层的失效方式全是静默的。探针（`probe_night`，另开一页独立跑，避免操作链的终局模态与开局推近动画污染读数）做的是**同机位配对对照**，而不是只测「夜面黑不黑」：

| 对照 | 翻的开关 | 实测 |
|---|---|---|
| 压暗壳 | 夜面机位把 `dim` 归零 | 0.118 → **0.209**（去掉压暗后亮回来） |
| 还原性 | 把 `dim` 写回 0.92 | 0.118 → **0.118**（无粘滞，A/B 结论可信） |
| 两壳合计 | 夜面机位把两壳一起关掉（= 改前） | 0.118 → **0.207** |
| 开局视角 | 开局机位把两壳一起关掉（= 改前） | 0.170 → **0.224** |
| 夜面灯火 | 东亚灯火机位把 `gain` 归零 | 亮度 **+0.025**、被照亮像素 R−B **+0.050** |
| **改前配方** | 东亚灯火机位 `setNightKneeK(0)` + `setNightTint(0xfff2e0)` | 亮度 **+0.031**、变暖 **+0.060**、纯白斑 **0.21%** |

最后一行是本轮新增的**「复现改前」配方**：不靠历史截图，而是在同一机位、同一帧率下把软膝关掉、把颜色写回暖金，现场重演旧效果 —— 这才让「改后比改前好」成为可复核的断言（`彩度保留更高`、`ΔR−B 更小`）。

灯火的观察点必须挑**灯火密集**的夜面：反日点落在澳洲中部荒漠，开灯关灯的读数只差 0.002，拿它验灯火等于没验；东亚夜面（中国东部 + 朝鲜半岛 + 日本）是全场最密的灯火带。

关于「暖度」的度量口径踩过两次坑。第一次：直接用「亮度 > X 且 R−B > Y 的像素占比」测不出灯火 —— 白天陆地表本身就偏暖（实测白天球面该占比 0.006，比夜面还高），而灯火核心被 ACES + sRGB 压向白色、R−B 随亮度反而收窄，阈值一高就漏。改成配对差分后才有意义：只看「关灯后明显变暗」的像素，问它们平均亮了多少、平均变暖了多少。第二次：**冷白灯火下 `dWarm` 依然是正的**（0.0496），一度看着像「说好的冷白呢」。原因是 `dWarm` 量的是 Δ(R−B)，而夜面底色本身强蓝（R−B ≈ −0.11），**任何**提亮都会把 R−B 抬上去。所以这条只做**同机位配方比大小**（冷白 0.0496 < 暖金 0.0600），不设绝对阈值。

图存在 `docs/shots/`（不入库，可由 `tests/smoke-render.py` 重新生成）：`smoke-12-day-face.png` / `smoke-13-night-face.png` / `smoke-14-lights-face.png` 是三个观察点，`smoke-11-night-home.png` 对 `smoke-19-home-before.png`、`smoke-13-night-face.png` 对 `smoke-18-night-before.png`、`smoke-14-lights-face.png` 对 `smoke-16-lights-off.png`、`smoke-14-lights-face.png` 对 `smoke-20-recipe-before.png` 是四组同机位对照（最后一组就是上表的「改前配方」）。

### 为什么「飞机朝向」要单独一层

**姿态错误是静默的**，而且它同时躲过了现有所有层：功能断言覆盖不到（那段代码依赖 THREE 与相机），像素体检只知道「有亮点」不知道亮点朝向，实机操作链只验证「点了有反应」。

实机反馈的现象是「有些飞机倒着飞」。根因在 `render.js` 的朝向推导：

```js
t = t < 0.5 ? t * 2 : (1 - t) * 2;   // 折叠成三角波 → t 是「弧上位置」
var fwd = (t < 0.5) ? 1 : -1;        // ← 拿位置判方向：位置每周期被经过两次，与方向无关
```

`t` 在一个往返周期里被**经过两次**（去程一次、回程一次），所以「`t` 落在哪一半」根本不含方向信息。正确做法是由**周期相位**推出方向，并把它抽成纯函数 `AT.geo.legAt(u)`，好让这条不变量能在**无头环境**里被永久钉住（`tests/headless.js` 的「往返航段层」）。

量到的偏差：离线探针在 30 组「航线 × 视角」里，每个航段有 **49.9%** 的相位在倒飞；实机读真实实例矩阵量到 **786 / 1580** 个判定样本倒飞（`dot = −1.00`，完全反向）。

三层的分工（缺一不可）：

| 装置 | 怎么判 | 为什么不能省 |
|---|---|---|
| `tests/headless.js` 往返航段层 | `fwd` 与 `dt/du` 同号；采样方向与真实位移同向（`dot>0`） | 纯几何、毫秒级、不依赖 THREE —— 日常改动后立刻能跑 |
| `tools/probe-heading.js` | 用真实 three.js 复算朝向公式，取机头方向 · 真实速度方向（`dot<0` 即倒飞），30 组场景 × 720 相位 | 覆盖多视角/多航线组合；**内置「修复前的错误公式」作为反例**，若反例未被检出则探针自报失效（否则「探针通过」没有证明力） |
| `tests/verify-heading.py` | 在真浏览器里**读渲染层真实的实例矩阵**，解出机头世界方向，与逐帧位移点乘 | 离线复算只能证明「公式对」，不能证明「画面上真的按这个公式来了」 |

`verify-heading.py` 有三个**必须写对**的判断细节（都踩过）：
- **必须由远侧（球背面）排除样本**：只判 NDC `z<1` 不够。球背面飞机的投影会翻号，算出的「机头屏幕向量」趋近零向量（实测出现过 `0.00px`），把它当退化样本会让判据量到噪声 —— 首版因此误报 15 个倒飞。加上「位于相机所在半球」后才干净（实测排除掉 1300+ 个远侧样本）。
- **采样窗必须长于一个完整往返周期**（`PLANE_PERIOD=14s`，最慢 `speed≈0.6` → 周期 ≈23s，故录 36s），否则只验到单程 —— 而这个 bug 恰好是「每个航段的一半」，只测一半周期有可能刚好躲过。脚本会统计掉头次数，为 0 直接判「覆盖不足」而不给通过。
- **必须在页面内按 rAF 节奏采样**：Python 侧 `page.evaluate` 往返一次几十毫秒，而退化帧只持续很短时间，慢采样抓不到相邻帧。故采样与统计都装进页面，Python 只取聚合结果。

截图前还会自动关掉季报模态 —— 录 36s 必然跨过季度结算，不关掉的话裁图截到的是弹窗文字。裁图放大拼接可用 `tools/zoom-planes.py` 复现（产物为过程截图，不入库）；不过飞机贴图在 390×844 下只有约 10px，**人眼核对只能作旁证，判定依据是实例矩阵**。

**一个被证伪的假设，记下来免得后人重走**：修倒飞时一度以为还存在第二类缺陷 —— 机头正对/背对相机时切向平行视轴，`atan2` 吃噪声导致姿态抖动（首版实机数据似乎支持：554 个样本里 22 个机头长度 <1.5px，最小 0.00）。但**排除远侧样本后不可测帧降到 0**（最小 4.68px），离线探针在 30 组场景里量到 `|sinθ|` 最小也有 0.083（阈值 0.05 从未触发）—— 那些 `0.00px` 测的是球背面飞机。所以 `render.js` 里保留的 `DEGEN_SIN` 退化保护是**廉价保险，不是已知 bug 的修复**，代码注释里也是这么写的。

方法论已沉淀为可复用技能：`~/.workbuddy/skills/rendered-heading-verify/`（含实机验证模板 `scripts/verify_heading.py`，原样放到本项目可跑）。

### 为什么「太阳位置」也要单独一层

和飞机朝向同理：**太阳算错了是静默的**。日下点偏 180°、赤纬用了错的形式、时角符号反了——这四种错法全都不会报错，球还是那个球，只是「白天那半边亮着灯」。而且它们躲过现有所有层：结构断言不碰天文，像素体检只知道「有亮点」。

`src/solar.js` 之所以做成**不依赖 THREE 的纯函数**，就是为了让这条链能在**无头环境**里毫秒级钉死。`tests/headless.js` 的「太阳位置层」16 条，分两组回答不同问题：

| 组 | 断言 | 回答 |
|---|---|---|
| 天文换算 | 赤纬极值落在 6/21 与 12/21、春分≈0°、本机 12:00→日下点经度 0°、经度恒在 [−180,180)、一天内自西向东单调绕行无跳变 | 「算对了吗」 |
| 几何对齐 | `ll2v ↔ v2ll` 严格互逆（6 个含极点的样本）、方向是单位向量、异常输入不产 NaN | 「与贴图 UV 约定对齐了吗」 |
| 机制生效 | （实机）真实时间的方向 **≠ 回退常量**、五处消费点同源 | 「机制真的在起作用吗」 |

最后一条是「机制写了 ≠ 机制生效」的直接应用：如果 `solar.js` 被短路或 `applySunAt` 没跑，太阳会停在回退值 —— 画面依旧「有个太阳」、**所有夜景读数照样全绿**，只有这一条会红。

**故障注入验证**（照例做了，否则不知道断言有没有牙）：时角符号反 → 红 3 条；赤纬换成简陋 sin → 红 1 条；`ll2v` 经度约定偏 180° → 红 1 条。还原后 253/253。

> ⚠ **实机夜景探针必须把时钟锁到固定机位**（`tests/smoke-render.py` 里 `setSunDir(FALLBACK_SUN_DIR)`）。不锁的话，探针每一条门槛都会变成**日期的函数**——同一个断言今天绿、明天红，读数也没法和上面那张标定表对照。锁定后实测读数与历次完全一致（day 0.4026 / night 0.1177 / ratio 0.2924），标定口径的可比性得以保住。

**音频为什么要单独一层**：音频 bug 是**静默**的。去抖窗口写错、总线接错、包络峰值为 0 都不会报错，只表现为「某个音没响」——这在无头 CI 里没人听得见、在实机里又容易归因成「我手机喇叭小」。`tests/audio.js` 用假 `AudioContext` 把每个音的**结构性事实**钉住：起了几个振荡器、频率多少、接到哪条总线、峰值是否为正。

**兼容层验的是两件不同的事**：`check-chrome61.py` 是**静态扫描**（扫 zip 内产物，逐条核对禁忌清单）；`check-fallback.py` 是**降级路径行为验证**（强制屏蔽能力，看页面是否仍可用）。后者的末尾会明确打印「本机无 Chrome 61 内核，未实测」——**降级逻辑写对了 ≠ Chrome 61 上真能跑**，交付说明中须保留该标记（见 minitool `css-compatibility.md §7`）。

契约层的方法论已沉淀为可复用技能：`~/.workbuddy/skills/web-ui-contract-check/`。

## 协作约定

- **不要主动 `git commit` / `push`**；改动完成后汇总说明，由用户决定
- 改动 sim 逻辑后，`headless.js` + `balance.js` 必跑；改动 UI 后，`ui-contract.js` + `smoke-render.py` 必跑；改动音频后，`audio.js` 必跑；**改动渲染层（尤其飞机/弧线/相机）后，`probe-heading.js` + `verify-heading.py` 必跑**——姿态类错误不会让任何别的层变红
- **改动光照 / 后处理 / 贴图后，`smoke-render.py` 的昼夜夜景探针必跑**（`[昼夜 / 夜景验收]` 那张表）——夜面变亮、灯火消失、昼夜比失衡都不会报错，只会「看着不对」。标定新参数时顺手把探针里的门槛与 README 的读数一起更新，别只改一处
- **改太阳方向只能走 `setSunDir()`**（`render.js` 模块级函数），不要直接改 `SUN_DIR` 数组元素。这个方向被**五处**消费（主光/补光/压暗壳 uSun/灯火壳 uSun/经纬网顶点色），漏任何一处晨昏线就错开且不报错。改完跑 `tests/smoke-render.py` 的「太阳方向」那 6 条断言（它们逐处核对同源）
- **改 `src/solar.js` 后跑 `tests/headless.js` 的「太阳位置层」**（16 条，毫秒级）。日下点算错是静默的 —— 球还是那个球，只是「白天那半边亮着灯」。新加断言时照例做故障注入（时角反号 / 赤纬换形式 / 经度偏 180° 三种注入各应打红对应断言）
- ⚠ **在 `render.js` 的 `init()` 内部不要引用 `api.<成员>`**：`init` 就是被 `api.init` 调用的，此刻 `api` 字面量还没求值完，读到的全是 `undefined`（或写进一个马上被丢弃的临时对象）。踩过两次：`api.applySunAt` 直接抛 TypeError 导致**整个渲染初始化静默失败、画面停在纯黑**（五层测试里只有夜景探针能看出来 —— 它表现为「所有读数退化成同一个值」）；`api.openAtNight = x` 赋值打水漂（读出来恒为 false）。导出面一律用 **getter**，或把实现放模块级由 `init` 与导出面共用
- **改灯火亮度/颜色前先想清楚是不是在动软膝。** 灯火这条链上有三个互相拉扯的量：城市核亮度、弥散辉光面积、峰值截断。只调 `NIGHT_GAIN` 会同时动三个，所以重定它要走 `tools/probe-night-gain.py` 扫一遍，别凭肉眼。**软膝必须作用在增益之后**（`lum × uGain` 再进膝），写成「先压后增益」上界立刻失效、纯白斑原样回来
- **往夜景里加会发光的元素时，先确认它落在哪个绘制批次。** 透明批次（`transparent: true`）无论 `renderOrder` 写多小都在压暗壳**之后**绘制，压不成暗 —— 经纬网就是这么被漏掉的。夜面要压暗的东西一律走**顶点色烘焙**或自己乘 `night` 因子
- 重新生成夜面灯火贴图必须走 `tools/make_night_texture.py` → `tools/gen-earth-night-tex.js` 两步，且先确认 `assets/earth.jpg` 未变（md5 `e15eb8d2…`）；贴图是内联进包的，**改完贴图必须重打包**
- **改了任何源码后都要重打包，再跑 `check-chrome61.py` / `verify-dist.py`**——这两个脚本扫的是 **zip 内产物**，不重打包会拿旧包给出**假绿**。踩过两次：一次是 `audio.js` 加入后仍报「未使用 WebAudio」；一次是 `sim.js` 改了 17 行、`air-tycoon.zip` 还是旧包，八层却「全绿」。`tools/build_dist.py` 会打印「内容有变化：xxx」以提示差异，别忽略这行。
- 保持零构建、零依赖；不引入 CDN 与外部资源
- **`localStorage` 只允许出现在 `src/save.js`**（小工具规范 §2.4 的降级路径，且须包在 `try/catch` 内）。要加持久化需求请复用 `AT.save`，不要在别处直接读写浏览器存储 —— 否则 `tests/check-chrome61.py` 的 ⑤b 会失败
- 不擅自改动单位口径与需求压缩系数（会连带破坏玩法闭环）
