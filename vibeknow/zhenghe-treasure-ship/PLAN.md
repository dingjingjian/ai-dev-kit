**参数交接的教训**：v1 让 Blender 用正则去猜 `ship-params.js` 的源码，连摔三次

**重建中新增的设计约束（改动前务必知悉）**

| 约束 | 原因 |
|------|------|
| 桅基 = `deck_z(t)`，**不得**因桅落在楼内而抬到楼面 | 桅是自甲板一通到顶的整根木料，楼阁「套」在桅外。早先按楼面抬基，把中舱那根桅抬高 1.3，直接抹平了桅高弧线 |
| 帆面 `xc0/xc1` 分别给下缘/上缘 X 中心 | 帆必须随桅后倾，否则撑条会顺着斜桅漂出帆面 |
| 舵以全局 `KEEL_MIN_Z` 为基准，不用局部 `keel_z(t)` | 首尾有龙骨弧线，用局部值舵会悬在半空 |
| 站位 t 一律由顶点世界坐标反推 | `MB.build()` 把顶点直接写在世界坐标里，`object.location` 恒为原点，反推会全落到船中 |
| 对称部件名须能被拆解分组前缀覆盖 | `BowCap`/`SternCap` 曾因不以 `Hull_Shell` 开头而漏出分组 |

**命名规范**（`ZH_<部件>_<细分>`，供 HTML 拆解模式按前缀取件）：

### 阶段 3　GLB 导出与体积压缩

导出已通（`headless_check.py` 末尾自动导出）。**压缩与内联未开始。**

| 步骤 | 做法 |
|------|------|
| 压缩 | Draco 或 Meshopt 网格压缩；无贴图，用逐面材质索引即可 |
| 体积预算 | 先按 GLB ≤ 1.2 MB 试（当前 806 KB，未压缩已达标） |
| 内联方案 | GLB → Base64 → `assets/ship-data.js`（同 `moon-landing-3d` 的内联贴图做法），保证 `file://` 可跑 |
| 降级 | 运行时按设备能力选精度；低端机加载低模版 |

> ⚠️ **风险点**：Base64 膨胀约 33%，806 KB → 约 1.05 MB。
> 若超预算，退路依次是 ① 提高压缩率 ② 拆「船体 + 桅帆」两段按需加载
> ③ 改用手写引擎的参数化几何（不导 GLB，直接代码生成）。**第 ③ 条最省**，见阶段 4。

### 阶段 4　HTML 展示页

**技术选型（需你拍板，这是本计划最关键的决策）**：

| 方案 | 做法 | 优 | 劣 |
|------|------|----|----|
| **A. 经典 three.js 内联** | 把 three.js 打包进 `assets/` 内联 | 生态成熟，GLB 加载省事 | three.js 压缩后仍约 150 KB+，加上 GLB 易超预算 |
| **B. 复用手写 WebGL 引擎** | 沿用 `moon-landing-3d/assets/engine.js`，自己写 GLB/几何加载 | 引擎已被验证可在小程序容器跑；体积极小；可控 | 需自己写精简 GLB 解析 |
| **C. 混合** | 引擎用手写（B），几何**不导 GLB 而用代码参数化生成** | 体积最优（零模型文件）；Blender 只作设计验证与截图 | 放弃 Blender 产物的直接复用 |

> **我的建议：C。** 宝船是**规则几何体**（船体是截面放样、桅帆是柱面 + 弧面薄板），
> 参数化生成比 GLB 更小更灵活，且天然支持「拆解」的逐部件控制与「航行」的动态形变。
> 更关键的是：`assets/ship-params.js` **已经是唯一真源**，曲线控制点与采样表都在里面，
> HTML 端直接用同一套 `interp()` 生成几何即可与 Blender 侧严格一致 —— 这是现成的红利。
> 若你希望 Blender 是唯一真源（后续要换渲染、出周边、做 3D 打印），则应选 A 或 B。

**三种模式**：

| 模式 | 交互 | 内容 |
|------|------|------|
| 展示 | 单指拖拽旋转、双指缩放、双击复位 | 宝船整体 + 热点标注（点击桅/舵/隔舱出说明） |
| 拆解 | 拖动进度条或点击部件，部件沿法线铺开 | 按 8 组分层展开，组名见 `EXPLODE_GROUPS` |
| 航行 | 时间轴推进 | 船队编队、针路连线、季风与七次航行的节点 |

**适配要求**：竖屏移动端优先（桌面端居中 480px）；安全区（`env(safe-area-inset-*)`）；
Chrome 61 基线（不用可选链、不用 `??`）；触摸事件优先。
